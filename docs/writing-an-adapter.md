# Writing a marisjs Adapter

This is a concrete walkthrough of writing a marisjs deployment adapter for a new
platform. It proves the [adapter interface](adapter-interface.md) is sufficient by
showing exactly what an adapter author needs to know — and what they don't.

The example platform is **Cloudflare Workers**, chosen because it's structurally
different from both Node.js and static hosting: edge functions that run in a V8
isolate, a proprietary module format (ES modules with `export default { fetch }`
entry point), no Node.js standard library, and a build-step requirement (`wrangler
deploy`). If the interface works for this, it works for anything.

## What you need before you start

Two documents. That's it:

1. **[Adapter interface spec](adapter-interface.md)** — the contract between `marisjs
   build` output and any adapter. Read this once. It's ~400 lines.
2. **Your platform's deployment docs** — you need to know what format your platform
   expects. For Cloudflare Workers: a single JavaScript file that exports a `fetch`
   handler, deployed via `wrangler`.

You do **not** need:
- The marisjs grammar spec
- The compiler source code
- Knowledge of signals, components, or reactivity
- Any of the framework's language rules

## Step 1: Understand the build output

Every marisjs adapter starts the same way: read `routes.json`.

```json
{
  "version": 1,
  "runtime": "./runtime.mjs",
  "routes": [
    {
      "path": "/",
      "file": "index.html",
      "mode": "server",
      "css": ["styles/main.css"],
      "clientModules": [
        { "name": "Cart", "path": "./components/Cart.mjs" },
        { "name": "Header", "path": "./components/Header.mjs" }
      ]
    },
    {
      "path": "/about",
      "file": "about.html",
      "mode": "static",
      "css": []
    }
  ]
}
```

From this manifest alone you can answer every question the adapter needs to answer:

| Question | Answer from manifest |
|----------|---------------------|
| What URL paths exist? | `routes[].path` |
| What file do I serve for `/about`? | `routes[1].file` → `about.html` |
| Does `/about` need SSR? | `routes[1].mode` → `"static"` (no) |
| Does `/` need SSR? | `routes[0].mode` → `"server"` (yes) |
| Which CSS files does `/` need? | `routes[0].css` |
| Which client components hydrate on `/`? | `routes[0].clientModules` |

The answer to "what file do I serve" is always in the manifest. You never need to
inspect the output directory yourself.

## Step 2: Decide which modes you'll support

Every adapter must handle `mode: "static"` — it's the simplest case. You can choose
whether to support `mode: "server"` or reject it.

**For Cloudflare Workers**, we'll support both:

- **Static routes**: upload the HTML file (and its CSS/JS dependencies) to
  Cloudflare's static assets (Workers Assets, or KV).
- **Server routes**: bundle the page module into the Worker script so it can
  re-execute at the edge on every request.

If you were writing an adapter for a purely static platform (S3, GitHub Pages), you'd
reject `mode: "server"` routes — just like `@marisjs/adapter-static` does.

## Step 3: Handle static routes

For every `mode: "static"` route, the HTML file listed in `routes[].file` is
self-contained — it already has the import map, CSS links, and client hydration
scripts embedded. You just need to serve it.

For Cloudflare Workers, this means putting the HTML file somewhere the Worker can
return it:

```js
// In the adapter's generated Worker:
if (route.mode === 'static') {
  return new Response(STATIC_FILES[route.file], {
    headers: { 'Content-Type': 'text/html' },
  });
}
```

The CSS files listed in `routes[].css` and the client module `.mjs` files listed in
`routes[].clientModules` must also be reachable. For Workers, you'd put them in
Cloudflare's static asset store. The manifest tells you exactly which files exist
and their relative paths.

## Step 4: Handle server routes (the interesting part)

A `mode: "server"` route needs to execute its page module at request time. For
Cloudflare Workers, the page module IS the Worker code — not a separate Node.js
process. This means the adapter needs to bundle the page module into the Worker
script.

The adapter reads `route.file` (e.g., `index.html`), derives the corresponding
`.mjs` file (`pages/Index.mjs` — replace `.html` with `.mjs` and look for the
page module at the expected location in the output directory), and imports it into
the Worker:

```js
// Generated by the adapter at build time:
import { Index } from './dist/pages/Index.mjs';
import { Cart } from './dist/components/Cart.mjs';
import { Header } from './dist/components/Header.mjs';

const routeMap = {
  '/': { component: Index, clientModules: ['Cart', 'Header'], css: ['styles/main.css'] },
  '/about': { html: STATIC_FILES['about.html'] },
};

export default {
  async fetch(request) {
    const url = new URL(request.url);
    const route = routeMap[url.pathname];
    if (!route) return new Response('Not found', { status: 404 });

    if (route.html) {
      return new Response(route.html, { headers: { 'Content-Type': 'text/html' } });
    }

    // Server route: call the component
    const result = await route.component({});
    const serverHtml = typeof result === 'string' ? result : result.html;

    return new Response(htmlShell(serverHtml, route), {
      headers: { 'Content-Type': 'text/html' },
    });
  },
};
```

**The key insight**: the page module exports a plain function that takes `props`
and returns HTML (or `{ html }`). The adapter doesn't need to know how the function
works internally — it just calls it. This is the entire server-side contract from
the interface spec.

The `htmlShell` function is the same standard HTML wrapper documented in the
interface spec (Section 4). Every adapter generates it identically — import map,
CSS links, client hydration script. You can copy it verbatim from the spec.

## Step 5: Handle the runtime

The `import { signal } from '@marisjs/runtime'` statements in client modules need to
resolve. For **browsers**, this is handled by the import map in the HTML shell:

```html
<script type="importmap">
{ "imports": { "@marisjs/runtime": "./runtime.mjs" } }
</script>
```

The adapter just needs to serve `runtime.mjs` as a static file at that path. For
Cloudflare Workers, put `runtime.mjs` in the static assets bucket.

For **the Worker itself** (when importing page modules that reference
`@marisjs/runtime`), the adapter can bundle `runtime.mjs` directly into the Worker
script so ES module imports resolve at build time, or it can use an import map in
the Worker's `wrangler.toml`. Either approach works; the interface doesn't prescribe
one.

## Step 6: Package everything for the platform

Cloudflare Workers expects:

1. A Worker script (the generated JavaScript from Step 4).
2. A `wrangler.toml` configuration file.
3. Static assets (HTML, CSS, client `.mjs` files, `runtime.mjs`) uploaded via
   Workers Assets or Workers KV.

The adapter's job at this step is purely mechanical: generate the platform-specific
config from the manifest data.

```toml
# Generated wrangler.toml
name = "my-marisjs-app"
main = "worker.mjs"
compatibility_date = "2026-07-30"

[assets]
directory = "./static"
```

The adapter writes the Worker script, copies static files, and writes the config.
It never parses a `.tsx` file, never validates a component, never touches the
compiler.

## Complete adapter structure

A real adapter is typically a small script or package. Here's the full file list
for `@marisjs/adapter-cloudflare`:

```
packages/adapter-cloudflare/
├── cli.mjs      # Reads manifest, generates worker + config + static dir
├── package.json
└── README.md
```

The `cli.mjs` is ~150 lines. It reads `routes.json`, loops over routes, generates
the Worker script from the manifest, copies static files, and writes
`wrangler.toml`. No compiler dependency. No framework insight. Just the manifest
and the HTML shell.

## What the interface guarantees you never need to touch

This is the most important section. An adapter author working from the interface
spec alone never needs to:

| Concern | Why it's not your problem |
|---------|--------------------------|
| How TSX files are parsed | The compiler produces `.mjs`, `.html`, `.css` — you consume those, not `.tsx`. |
| Component validation rules | The compiler validated everything before writing the build output. Invalid components don't reach the adapter. |
| Signal reactivity | `runtime.mjs` handles it. Your adapter just serves the file. |
| `data()` implementation | You call the page component function — `data()` runs inside it. You don't implement it. |
| CSS scoping or processing | CSS files are listed in the manifest by relative path. You copy and link them. |
| The import map | Fixed format. Copy it from the spec's HTML shell template. |
| Route derivation from filenames | The manifest has URL paths. You never see filenames except the ones in `routes[].file`. |
| How client hydration works | The compiler embeds `mount()` calls in the HTML. Your adapter just includes them in the shell. |

## Checklist for any new adapter

1. Read `routes.json` — this is your only input beyond the files themselves.
2. For each route with `mode: "static"`, ensure the `.html` file and its
   dependencies (CSS from `routes[].css`, client modules from `routes[].clientModules`,
   `runtime.mjs`) are served as static files.
3. For each route with `mode: "server"`, either (a) import and call the page
   component function from the corresponding `.mjs` module, wrapping the result in
   the standard HTML shell, or (b) reject it with a clear error if your platform
   doesn't support SSR.
4. Generate any platform-specific configuration files (`wrangler.toml`,
   `vercel.json`, `netlify.toml`, `Dockerfile`, etc.) — these are always generated
   from the manifest data, never hand-written.
5. Write a README showing `marisjs build && your-adapter ./dist ./out`.

If you find yourself reaching for the compiler source or the grammar spec, the
interface is missing something — file an issue.
